# 每日计划模块开发过程与交付记录

日期：2026-10-03。需求规格：[每日计划模块需求规格与设计](11-daily-plan-spec.md)。本轮遵照用户要求设计与开发，未新增测试用例，未提交或发布安装包。

## 1. 基线与问题

工程已经存在 V1.0 工作区、计划实体、需求会话和原子持久化；工作目录含大量此前未提交的修改。本轮在现有内容上增量开发，未清理或重置既有工作。

每日计划基线仅包含日期、标题、项目及状态循环操作。日历只读今日；没有独立编辑、状态筛选、重要性、用时、说明、历史建议或移除流程。已知 Builder 按值参数会保留旧数据，模块必须读取最新 @State 快照。

## 2. 方案与决策

- 完整列表与编辑分成两个路由，避免添加表单遮住当日行动列表。
- 保留三种原有状态，通过三个明确按钮直接选择；保持原数据兼容，不新增完成评分。
- 预计用时为自填计划值，不推算实际效率；重要性只影响完整列表排序。
- 改期修改原 ID；建议采纳新建 ID，区分移动原事项与安排后续行动。
- 移除由用户就地确认，保留需求会话与历史；不删除日历原事件。
- 日历按所选日读取，将用户选定的会议保存为带来源快照的事项，单独合并时间占用。
- 先交付可解释的本机规则建议；个性化 AI 建议保留协议设计与明确未接入状态。
- 提醒沿用已有普通系统注册链路，提供“制定明日计划”预填入口；不将打开应用冒充模块直达。

### 2026-10-04 · 刷新日历出现两条相同记录：原因分析

用户反馈刷新后看到两条相同记录，明确要求先解释、不直接修改代码。

源码核查：NativeData 遍历 getAllCalendars 返回的日历，按“日历 ID / 事件 ID / 实例起始时间”去重；标题和显示时间相同并不构成去重条件。Index 刷新先清空日历数组，成功后替换，并有 busy 防重入；没有把新结果追加到旧数组。日历候选仍保留已导入项，因此同一事件也可能分别出现在上方计划和下方日历区域。

分析结论：若两条均在日历候选列表内，优先核查不同来源/事件标识产生的相同显示内容；跨日历副本、同日历不同事件 ID 均是候选解释，不是已确认的设备事实。若分处计划和日历区域，则符合现有双区展示。现有模拟用例只证明相同实例 key 被过滤，不能证明用户设备此次返回的两条是什么关系。

待核实：两条记录所在区域、calendarId/eventId/实例起止时间及全天标志，必要时来源日历信息；只需最少诊断字段，无需收集完整日历正文。确认前不按标题或时间静默合并，避免误删独立事件。

本轮仅阅读源码和既有测试、更新规格及问题分析文档；未修改生产代码、未新增或执行测试，也未读取用户设备日历。
