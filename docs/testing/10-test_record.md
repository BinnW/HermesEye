## 问题1：键盘遮挡内容

问题修复状态：已修复，模拟器竖屏自动回归通过；其他页面待用户复测

输入法键盘弹出的时候，会把屏幕内容给挡住，影响体验，需要在键盘弹出的时候优化页面显示逻辑，起码把内容都显示全，而且可以在屏幕剩余部分滑动。

### 解决方案（2026-10-02）

- 使用 `KeyboardAvoidMode.RESIZE_WITH_CARET`：键盘弹出时缩小页面，并跟随多行输入光标避让。
- 通过窗口键盘高度事件隐藏／恢复手机底部导航，不以输入框是否聚焦判断键盘是否显示。
- 主体滚动区占用剩余空间；避免固定提示占用输入空间；后续问题4已将操作反馈统一改为 Toast。
- 多行输入框限定可视高度，长文本在框内滚动；其余内容及提交按钮可通过页面滚动到达。
- 键盘开合不清空草稿、不触发路由恢复或主动滚动到页面顶部；页面销毁时清理监听，忽略迟到回调。

### 回归设计（2026-10-03）

| 层次 | 用例 | 覆盖 |
|---|---|---|
| Node 服务套件 | S12–S15 | 避让模式、初始键盘态、迟到监听、重复启动 |
| 设备 UI Hypium | U03 | 新建项目页：导航隐藏/恢复、滚动区收缩、多行输入、草稿保留 |
| 手动验收 | D13-① | 连接表单、会话、记录、计划各页逐框输入；横屏、大字号、不同输入法 |

### 验证结果

见 [发布与验收记录](../05-release.md) 中的“键盘遮挡修复”。


## 问题2：会话页面不显示上次会话结果

问题修复状态：代码已修复（2026-10-03）；设备端两轮收发按 D13-② 待验收

每次“项目”页签下进入会话页面后，输入内容并且得到Hermes的返回后，不再页面上自动更新会话内容，需要重复进入一次会话页面才会显示。

### 根因分析（2026-10-03）

`Index.ets` 的 `send()` 流程本身正确：深拷贝工作区 → 在副本上追加用户消息与回复 → 原子保存 → `this.data = next` 整体替换。问题在 UI 绑定层：

1. `chat(need: Need)` 以**按值参数**接收 `need`（`this.chat(this.selectedNeed() as Need)`）。ArkUI 中按值传递的 @Builder 参数在参数对象更换时不会触发 builder 内部 UI 刷新——builder 仍渲染发送前的旧 `need` 对象，其 `messages` 永远停留在进入页面时的快照。
2. 重新进入页面时 builder 以新对象重建，所以消息“回来”了——与实测现象一致。
3. 次级风险：`ForEach(need.messages, ..., (_m, index) => String(index))` 以序号为键，若未来支持删除/重排消息会渲染错位；当前仅追加，暂不构成缺陷。

### 解决方案（2026-10-03）

消息列表改为 `ForEach(this.selectedNeed()?.messages ?? [], ...)`，在更新回调中读取最新 `@State data`，不再使用进入会话时的 `need.messages` 快照。保持现有发送、保存、消息顺序与上下文授权逻辑。发送中气泡和加载位置由问题3单独处理。

旁证：同日“日历内容响应式刷新修复”（[05](../05-release.md)）确认为同一模式——日历字符串按值传入 `@Builder hint`，闭包保留初始文本导致展示不更新。会话页属同类缺陷。

### 回归设计（2026-10-03）

| 层次 | 用例 | 断言 |
|---|---|---|
| Node 工作区套件 | W17、W18 | 发送提交只写入新快照；旧对象引用不含新消息——页面必须渲染最新 `data` |
| Node 工作区套件 | W46 | 页面源守卫：会话页从最新 @State 读取消息，不渲染进入时快照 |
| Previewer Hypium | L05、L06 | 同上，真实 ArkTS 运行时复核 |
| 设备 UI Hypium | U05（待启用） | 需可达 Hermes 或桩服务后自动化：发送→回复原地出现 |
| 手动验收 | D13-② | 项目/计划/独立三入口进入会话→发送→回复原地出现，不重进；连续两轮收发均原地刷新；返回再进入历史一致；杀进程重进历史完整、未重复发送 |

手动验收步骤（修复后执行，逐项打勾）：

1. “项目”页签 → 项目详情 → 进入需求会话 → 发送“回归一” → **不离开页面**等待回复 → 回复与原消息同时可见。
2. 同页继续发送“回归二” → 第二轮问答原地追加。
3. 返回再进入该会话 → 两轮问答各出现一次，无重复无丢失。
4. “今日 → 计划事项 → 继续事项会话”与“项目 → 独立需求 → 继续会话”两入口重复步骤 1。
5. 杀进程冷启动重进会话 → 历史完整；连接断开后重连不产生重复发送。

### 验证结果

本轮构建与回归结果见 [05](../05-release.md)；未将领域快照测试等同于实际 UI 收发验收。

## 问题3：发送后未立即显示消息，加载动效位置不合理

问题修复状态：代码已修复（2026-10-03），自动回归与构建通过；设备交互待验收

点击“发送给 Hermes”后，输入内容没有立即出现在会话中，加载动效显示在页面最上方。预期是在会话末尾显示用户消息，并在其下方显示等待状态。

### 根因分析（2026-10-03）

`send()` 原先在收到回复后才一起追加用户消息与助手消息，网络等待期间没有可显示的用户气泡。加载和停止控件位于页面公共顶部，与当前消息脱离。此问题与问题2的“收到回复后不刷新”属于不同阶段。

### 解决方案（2026-10-03）

- 校验和凭据读取完成后，立即显示临时用户气泡，下方显示“正在等待 Hermes”和停止按钮；发送时滚动到气泡。
- 临时消息按服务器空间和会话区分，与正式历史分开；成功保存后由正式问答替换，不重复追加输入。
- 请求期间阻止重复提交；网络失败或停止后保留输入和就地错误，不自动重发，并说明服务端可能仍在执行。
- 回复保存失败时保留内存中的回复供复制，移除临时气泡并阻止继续写入。

尚未实施：仅重试本机保存的按钮、用户上翻时的“有新消息”提示。未保存回复仍需在退出应用前复制。

### 回归设计（2026-10-03）

| 层次 | 用例 | 断言 |
|---|---|---|
| Node 工作区套件 | W35、W38 | 生产 send()：请求未结束时已有临时气泡与 pendingKey；失败后就地保留尝试内容与错误 |
| Node 工作区套件 | W36、W37 | 网络失败保留输入、不重试；保存失败回复留内存、临时气泡不残留、阻止继续写入 |
| Node 工作区套件 | W39 | 成功时若已切走会话，只清原会话草稿，不触碰当前输入 |
| Node 工作区套件 | W46 | 页面源守卫：临时气泡位于历史之下、输入区之上；等待中重复点击只发一次（W35） |
| 手动验收 | D13-③ | 慢响应、停止、连续收发、跨页返回：气泡和加载位置正确，输入不丢失，结果不串会话 |

手动验收步骤：

1. 输入消息并发送，不离开页面，确认用户气泡立即出现，等待动画和停止按钮位于其下方。
2. 等待期间重复点击发送，确认只有一次请求；收到回复后无重复气泡。
3. 连续发送两轮，再返回并重进，确认正式历史一致。
4. 分别验证断网、停止等待和保存失败；确认输入或回复可保留、复制，不自动重发。
5. 打开键盘、上翻历史及跨页返回，检查消息位置和所属会话。

### 验证结果

生产 `send()` 等待、成功、重复点击、网络失败及保存失败回归通过；DevEco 主包与设备测试包构建通过。已更新并启动模拟器，实际气泡位置、停止操作与真实 Hermes 收发仍待设备验收，见 [05](../05-release.md)。

## 问题4：操作提示集中在页面顶部，反馈不易察觉

问题修复状态：代码已修复（2026-10-03），构建通过；Toast 设备交互待验收

发送消息、连接 Hermes 等操作的反馈均显示在页面顶部“提示”区域。页面滚动后不易看到结果。预期操作反馈统一使用 Toast，不再单独占用顶部区域。

### 根因分析（2026-10-03）

`notice()` 原先写入全局 `feedback/failed`，根布局据此渲染提示块。提示位置与实际操作位置无关，长文本还会占用内容空间。

### 解决方案（2026-10-03）

- 保留 `notice()` 作为统一入口，内部调用当前 UIContext 的 Toast；所有通过该入口发出的操作反馈随之切换。
- 1.5 秒内重复的相同提示去重；普通提示显示 3 秒，错误提示显示 5 秒。
- 删除顶部提示块和公共加载动画，会话等待状态由问题3在消息下方展示。
- 连接状态、发送失败等持续业务状态保留在对应位置，不作为顶部提示重新出现。

尚未实施：独立 Toast 队列管理、长错误摘要与详情拆分。现有去重不等同于完整队列控制。

### 回归设计（2026-10-03）

| 层次 | 用例 | 断言 |
|---|---|---|
| Node 工作区套件 | W45 | 生产 notice()：1.5 秒内相同提示去重；普通 3 秒、错误 5 秒；超时后可再提示 |
| Node 工作区套件 | W47 | 页面源守卫：操作反馈经 showToast，无顶部残留提示块 |
| 手动验收 | D13-④ | 长页面、键盘、连续操作：提示可见且不挤占布局；相同提示短时间内不重复弹出 |

手动验收步骤：

1. 滚动到页面底部后保存或测试连接，确认无需返回顶部即可看到反馈。
2. 打开键盘后触发操作，确认 Toast 可见、输入区域没有因提示而缩小。
3. 连续触发相同反馈，检查去重；依次触发不同结果，检查提示是否清晰。
4. 触发会话发送失败，确认 Toast 消失后，所属会话仍保留错误信息。

### 验证结果

DevEco 主包与设备测试包构建通过，三套逻辑回归通过。尚无针对 Toast 展示的设备自动验收，显示位置、持续时间和连续操作效果待复测，见 [05](../05-release.md)。

## 问题5：读取日历后无法选择日程加入每日计划

问题修复状态：代码已修复（2026-10-03），自动回归与构建通过；系统日历导入交互待验收

刷新今日日历后只能查看文本，无法快速将日程加入计划。预期日程可以选择，经确认后生成当日计划事项。

### 根因分析（2026-10-03）

原来的日历读取直接返回拼接字符串，缺少可选择的结构化列表、稳定来源标识和计划导入逻辑。仅凭标题无法可靠区分同名日程或重复日程的不同实例。

### 解决方案（2026-10-03）

- 使用 `queryEventInstances` 查询真实今天发生的日程，保留日历、事件和实例时间标识，以及标题、起止时间和全天信息。
- 展示带选择框的日程列表；用户选择后，通过“确认将所选日程加入计划”提交。确认区明确日期，归属使用上方已选项目。
- 在当前服务器空间内按日历、事件和实例开始时间去重；已导入项显示“已加入”，重复导入跳过。
- 原子保存计划，新增可选 `calendarSource` 字段，兼容旧计划；新事项为待完成，不将会议自动计为完成。
- 导入成功后切换计划列表到日历日期。仅写入本机计划，不修改原日历，不自动上传。

尚未实施：来源日程变更/取消的对比提示及更新确认。刷新不会自动覆盖已导入计划。当前仍读取真实今天的日历，任意日期联动属于问题6。

### 回归设计（2026-10-03）

| 层次 | 用例 | 断言 |
|---|---|---|
| Node 服务套件 | S06–S08、S23–S25 | 拒绝授权不读取；实例时间与稳定标识；重复返回去重；无效标识报错；昨日/明日剔除、多日历合并排序；时间回退与全天缺省 |
| Node 工作区套件 | W40–W42 | 只导入所选项，同名不同实例不混淆，已有项不重复；空选择不导入；去重按空间独立 |
| Node 工作区套件 | W43、W44 | 非法 calendarSource 拒绝、旧计划兼容；超长标题导入整体失败、无部分持久化；副本导入不影响原快照（W41） |
| Previewer Hypium | L08、L09 | 导入去重/来源/项目与来源校验的真实运行时复核 |
| 手动验收 | D13-⑤ | 单选/多选、全天/跨天/重复日程展示正确，保存失败不部分写入，跨空间隔离，撤销权限明确报错 |

手动验收步骤：

1. 系统日历中准备当天普通、全天和重复日程，授权刷新后核对标题、时间与数量。
2. 选择部分日程和项目，确认导入；检查目标日期、项目、待完成状态及来源。
3. 再次刷新并导入同一日程，确认没有重复计划；同名不同日程可分别导入。
4. 只选择不确认，检查计划未发生变化；保存失败时检查没有部分导入。
5. 切换服务器空间后重复验证，确认计划隔离；撤销权限后刷新应明确提示失败。

### 验证结果

日历结构化读取与导入逻辑回归通过；DevEco 主包与设备测试包构建通过，已更新并启动模拟器。实际系统授权、日程类型展示及连续导入仍待设备验收，见 [05](../05-release.md)。

## 问题6：每日计划模块结构混乱，操作流程不完整

| 区域 | 内容与操作 |

## 问题7：刷新日历后出现两条相同记录

记录日期：2026-10-04。状态：用户反馈，已完成源码初步分析，具体设备根因待核实；用户要求先解释，本轮不修改代码。

当前读取所有可访问日历，去重键为 `calendar.id/event.id/instanceStartTime`（实例时间缺省时使用事件开始时间）。不同日历 ID、不同事件 ID 或不同实例起始时间均保留，页面主要展示标题和时间，因而可能出现内容看似相同但标识不同的两条记录。不同日历中的副本、同日历中不同 ID 的相同内容事件仅为待排查假设，尚无此次设备返回数据佐证。

刷新逻辑先清空再替换数组，且有 busy 防重入，没有追加旧结果的路径。另外，已导入的事项仍显示在日历候选区并标记已加入，因此计划区和日历区各出现一次也可能被理解为重复。

下一步定位所需证据：重复记录是否位于同一列表、两条记录的日历/事件标识、实例起止时间及全天标志。相同 key 的输入已有去重逻辑与模拟用例，但本轮未运行设备复现；不能直接归因于系统日历或断定界面渲染没有问题。

## 问题8：21 处 SDK 调用未处理 `@throws`，编译器逐点告警

记录日期：2026-10-04。状态：**已修复（2026-10-06），零 ArkTS 告警门禁通过；设备异常场景覆盖范围见下文**。发现方式为编译期告警审计（新 harness 引入），非设备复现。

### 现象

加固 harness 后，`scripts/verify.sh` 首次把 ArkTS 诊断纳入汇总，暴露出此前被忽略的告警：

- `hap-default` 21 条、`hap-ohostest` 1 条（后者为测试源码中的同类调用）；
- 文案全部一致：`Function may throw exceptions. Special handling is required.`；
- 分布：`WorkspaceRepository.ets` 9 处、`NativeData.ets` 6 处、`KeyboardAvoidance.ets` 3 处、`pages/Index.ets` 2 处、`CredentialStore.ets` 1 处。

证据：[最终流水线编译日志](validation/2026-10-04-final/hap-default.log)。

### 根因分析（2026-10-04）

不是代码笔误，而是系统性的规则未落实。HarmonyOS SDK 声明文件中，会抛异常的 API 以 `@throws { BusinessError } <code> - <说明>` 标注（SDK 内 **292 个 `.d.ts`** 使用该标注，如 `@ohos.security.asset.d.ts` 的 `remove()` 列出 `24000006`–`24000015` 等错误码）。ArkTS 编译器要求调用点处于 `try/catch` 中，否则每个未处理调用点各报一条 `WARN`。

同一文件内的对照最能说明问题：`services/CredentialStore.ets` 的 `asset.add`（14 行）与 `asset.query`（26 行）都有 `try/catch`，唯独 `asset.remove`（32 行）没有——这处漏网正是 1 条告警的来源。其余告警点同理，集中在 `fileIo.*Sync`、`window.getLastWindow`、`abilityAccessCtrl.createAtManager`、`calendarManager.*`、`notificationManager.requestEnableNotification`、`promptAction.showToast`、`setColorMode`。

影响面：这是**告警而非错误**，当前不影响编译与运行，因此不会被既有验证流程拦下；但它是真实的健壮性债务——设备侧权限拒绝、Asset Store 未解锁、文件系统异常等路径都依赖这些调用被正确处理。

### 解决方案（2026-10-06 已实施）

- 对照本机 SDK 声明逐点加 `try/catch`；异步 SDK 调用使用 `await` 后捕获拒绝。没有屏蔽诊断或关闭编译器检查。
- `PlatformErrors` 保留调用阶段与数值错误码，丢弃可能包含路径、凭据或业务正文的原始 SDK 文案；日志只含操作名和错误码。未知错误码仍报错，不当作成功。
- 文件存储：权限/只读、空间/配额不足给出不同恢复说明；仅 `access` 的文件不存在可走初始化。读取失败禁用后续写入；写入、刷盘或关闭失败均不替换旧文件，同时失败时保留主错误与关闭错误。
- 安全存储：锁定/拒绝访问、凭据缺失按码提示；保存失败不降级明文。删除时仅 `24000002`（凭据已不存在）视为已达到目标；其他删除失败抛出，配置事务的孤立加密凭据清理失败记录脱敏诊断。
- 日历：区分授权窗口错误、查询时权限撤销（201）、能力不支持（801）和服务错误，不返回部分日历结果或伪造空列表，手动计划保持可用。不改变日程查询日期、去重与导入规则。
- 通知/提醒：拒绝通知时不注册提醒；提醒限额（1700002）明确报错；仅取消已不存在的提醒（1700003）视为目标已满足。无自动重试。
- 窗口：初始化失败清理已挂监听；清理失败保留句柄供后续处理并使旧回调失效；已销毁窗口（1300002）记录诊断后容忍。
- Toast/主题调用移至 `SystemPresentation`。Toast 失败仅记录脱敏诊断，不使已经成功的保存变成失败，也不计入去重；主题失败继续交由页面既有恢复提示处理。页面结构、显示模式选项不变。

### 回归设计与已执行结果

- 新增 S26–S33 共 8 组服务行为测试：Asset 错误、文件系统各阶段失败、日历 SDK 错误、通知/提醒错误、窗口初始化/清理、Toast 与主题异常。

## 问题16：阅读/业务模块补用例时发现的实现问题（2026-10-11）

本轮为阅读模块与业务面板补齐组件流程用例（F11–F16）、后端用例（37→77）并新增后端行覆盖门禁（5 个模块 100%）。过程中发现以下实现与规格不一致，**均未修改生产代码**。

### 16.1 高 · 失败周期在元数据校验前就发布了新副本

- 位置：`backend/reading.py:188`（写回 `reading_books`）早于 `:193`（`parts()` 的元数据校验）。
- 规格：`docs/modules/19-reading-spec.md:17`「范围内全部来源成功后才发布新副本；失败保留上次副本」。
- 复现：先采集 `highlight-1`；再把来源换成 `{'id':'highlight-2','text':'new','location':'L'*4000}` 并 `cycle('c2')` → `cycle` 抛 `413 reading_metadata_limit`，但 `reading_books` 已含 `['highlight-1','highlight-2']`，且该 collection 记录为 `collected`（`error=reading_metadata_limit`）。上次成功副本已被替换。
- 影响：违反"失败保留上次副本"，用户会看到一次失败采集把成功结果覆盖成大杂烩。
- 处置建议：把 `parts()` 的元数据预校验（以及对合并后条目的容量复核）前移到发布之前，失败时整体回滚。

### 16.2 中 · 2000 条/500KB 容量边界只校验本次入参

- 位置：`backend/reading.py:172-177` 只校验 `snapshot['entries']`；`:185` 会把历史条目并回，之后不再复核。
- 规格：`19-reading-spec.md:35`「每书最多 2000 条、单条 16000 字、序列化不超过 500KB；超过边界显式失败」。
- 复现：先采集 2000 条 `a*`，再采集 2000 条 `b*` → 落库 `len(entries)=4000`（约 270KB），无报错。
- 影响：容量契约只在单次入参层面成立，长期累积可突破上限，后续整理/分页会放大成本。

### 16.3 中 · `Reading.start()` 不幂等，`stop()` 后无法重启

- 位置：`backend/reading.py:324-329`（每次调用都新建线程并覆盖 `self.worker`）；`stop_event` 在 `stop()` 后未清除。
- 规格：`19-reading-spec.md:27`「本地业务进程是本模块唯一周期执行者」。
- 复现：`start(); first=worker; start(); second=worker` → 两个线程同时存活；`stop()` 后两个线程退出，但再次 `start()` 的新 worker 立即退出（事件仍为 set），周期无法恢复。
- 影响：限于线程生命周期与"单一执行者"语义；`tick` 的 `nextAt` 在锁内原子推进，双 worker 不会重复提交 Hermes（已用例锁定）。

### 16.4 中 · 阅读周期 1–720 未在客户端校验

- 位置：`entry/src/main/ets/components/ReadingPanel.ets:80`。
- 规格：`19-reading-spec.md` §3「周期 1–720 小时」。
- 实际：`Number(this.interval)` 原样 POST，`0`/`721`/`NaN` 由服务端 `backend/reading.py:116-118` 以 400 拒绝；用户在本地看不到即时错误。用例 `bounds=[0,1,720,721,NaN]` 记录了该行为。

### 16.5 中 · 未勾选同意时「一键采集/整理」未禁用

- 位置：`ReadingPanel.ets:198` + `:105-109`（`action()` 的 enabled 只看 `!busy && connected`）。
- 规格：`19-reading-spec.md` §3/§4 要求同意后才采集。
- 复现：`connected=true`、`consent=false` 时调用 `collect` → 仍发出 `policy(consent:false)` + `collect` 两条请求并显示成功文案，最终由服务端 409 拒绝。

### 16.6 低 · 提问片段未校验属于选中原文

- 位置：`ReadingPanel.ets:91`；规格 `19-reading-spec.md` §5「来源片段必须属于选中原文」。
- 复现：`selectedEntry='e1'`、`quote='完全不同的一段话'` → 正常提交（选择条目会预填原文，但输入框可改）。
